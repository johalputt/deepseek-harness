# Agent Note: web-fetch-http 私有网络目标阻断

Status: implemented

[English](2026-08-25-web-fetch-ssrf-blocking.md) | 中文

## 问题

`@deepseek-ai/dsh-web-fetch-http` 以刻意推迟的 SSRF 原语形态交付：它验证 URL 形态（仅 http/https、拒绝内嵌凭证、长度上限），但对*名字解析到哪里*不做任何检查。模型提供的 URL 可以把 harness 的出站流量指向 loopback 服务、RFC1918/局域网主机，或云元数据端点 `169.254.169.254`——经典的服务端请求伪造路径，而抓取器恰恰运行在合法持有凭证的开发者机器与 CI runner 上，风险因此更尖锐。

[web 能力 seam Agent Note](2026-06-24-web-capability-seam.zh.md) 把这个缺口列为首要推迟事项，并设定了标准：先 DNS 解析后验证以对抗 rebinding，跨重定向逐跳重新验证，IPv6 边缘处理包括内嵌 IPv4 形态。所调研的参考实现均未做 IP 级阻断（OpenCode 对主机名做字符串前缀检查；Claude Code 依赖集中式主机名黑名单加提示词），没有可复制的实现。

对主机名做字符串检查从来都不够。`localhost`、`127.0.0.1`、`[::1]` 只是入门；攻击者控制的权威 DNS 服务器可以在验证阶段回答公开地址、在连接时刻回答私有地址（DNS rebinding / TOCTOU）；IPv4 还能藏进 IPv6 拼写（`::ffff:10.0.0.5`、6to4、NAT64），纯 v4 黑名单永远看不见它们。

## 决策

提供方新增 `blockPrivateNetworks`（插件 `Config` 默认**开启**；`HttpFetchLimits` 上的必填字段让直接消费方显式声明自己的选择）。启用时：

1. **逐跳预检**（`private-net.ts` → `assertPublicHost`）：每次请求前（包括每个重定向目标）直接判定字面 IP，主机名经平台解析器以 `{ all: true }` 解析；只要*任一*解析地址非公开，该跳即以 `WEB_PRIVATE_NETWORK` 快速失败，此时不存在任何套接字。
2. **连接时刻重新验证**：阻断开启时请求经由 undici `Agent({ connect: { lookup } })`，其 lookup 对套接字实际可能打开的地址重新验证。预检与连接之间解析结果发生变化也逃不掉：这封死了 rebinding 窗口，而不是收窄它。
3. **全答案语义**：一次解析返回的多个地址中有一个非公开就整体拒绝该域名，恶意权威服务器无法把私有记录藏在公开记录后面。

分类逻辑（`isPubliclyRoutableAddress`）对 IPv4 判定 loopback、0/8、10/8、运营商级 NAT 100.64/10、链路本地 169.254/16、私有段 172.16/12 与 192.168/16、IETF 协议分配、已废弃的 6to4 relay anycast、基准测试 198.18/15、TEST-NET 文档段、多播 224/4 与保留/广播段。IPv6 先解析为八组（支持 `::` 压缩、单个点分尾段、zone 剥离），再判定未指定/回环、唯一本地 fc00::/7、链路本地 fe80::/10、多播 ff00::/8、文档段 2001:db8::/32；而 IPv4 映射 `::ffff:0:0/96`、NAT64 `64:ff9b::/96`、6to4 `2002::/16` 会被解包并按其内嵌 IPv4 自身判定。无法解析的输入按失败关闭处理。

两处文法细节具有安全分量并有测试固定：点分十进制尾段只在整个地址的最后一个组件合法（`10.0.0.1::` 不会解析成一个无关的「公开」v6 地址）；存在 `::` 压缩时只允许出现在标记之后。

拒绝行为由配置拥有而非硬编码策略：`blockPrivateNetworks: false` 逐字节恢复普通的直接抓取——这正是把模型指向本机 loopback 开发服务器的部署所需的，也是本包测试夹具所用的。

### 范围之外

防线信任平台解析器：操作系统在 `getaddrinfo` 之外解析的名字（如 mDNS），或本地从不解析 CONNECT 目标的代理部署，都会绕过检查。这些形态需要部署级的出口策略，而不是提供方代码。

## 备选方案考量

**为什么不用主机名黑名单（OpenCode/Claude Code 的形态）？** 它只能拦截拼写，拦截不了目的地：解析到 `10.0.0.9` 的 `localhost.internal.example.com`，或任何 rebinding 记录，都能顺利通过。seam note 的决策明确要求先解析后验证；字符串列表只是被标成围栏的减速带。

**为什么不「解析一次、验证、连接到已验证 IP」？** 把 URL 改写为已验证地址会改变线上请求（`Host` 标头与 SNI/证书身份不一致），或者需要按协议分别实现钉扎机制；而且除非每次重定向都重写，「验证与使用之间的窗口」依然存在。分发器级 lookup 在 Node 自身的连接路径上取得同等的 TOCTOU 免疫，无需改写 URL，也不会漂移证书身份。

**为什么用 undici 而不是给全局 `fetch` 打补丁？** Node 环境的 `fetch` 接受 `dispatcher` RequestInit 字段只是非官方扩展；undici 自己的 `fetch` 才正式文档化了该选项。阻断路径使用 undici 让控制落在契约支持的表面上，未阻断路径则与今天的全局 fetch 保持逐字节一致。

**为什么默认开启而不是可选加固？** 这是 harness 唯一的 SSRF 防线，安全默认值与 seam note 的既定规则（「不得在能触达敏感内部目标的部署中启用」）一致，且不要求每个部署都知道该风险的存在。真正需要访问私有目标的部署有一行有文档的退出方式——此后配置不当会大声失败（`WEB_PRIVATE_NETWORK`），而不是静默放开网络。
